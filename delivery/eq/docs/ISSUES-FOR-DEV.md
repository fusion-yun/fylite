# 给 fylite_dev 的问题清单

来源：FYLite 磁平衡工作台在 EAST 多炮号上做纯磁重构时暴露的问题。
环境：rc3 发布内核（`libfylite_kernel.so` sha256 `f2632102…`，ABI 163）+ `standalone` 适配器 `demo.py`。
所有结论都有可复现的对照数据，路径附在每节末尾。

---

## 问题 1：早期炮号（≤97030）的磁探针通道名与实际硬件不符

**现象**

`facts/device/east` 的早期设备版本（`_valid_shots = [0, 97030]`）里，磁探针是顺序命名：

```
HBP1T, HBP2T, HBP3T, HBP4T, HBP5T, HBP6T, HBP7T, HBP8T, HBP9T, … HBP38T
```

而这一代机器实际（遗留映射 `B_PROBE_NODES_LEGACY`）是：

```
HBP1T, HBP2T, HBP3T, NHBP4T, NHBP5T, NHBP6T, NHBP7T, NHBP8T, HBP9T, …,
DBP25T, DBP26T, NHBP27T, NHBP28T, NHBP29T, NHBP31T, HBP32T, …, DBP36T, HBP37T, HBP38T
```

结果：按 `HBP{n}T` 取数时，

- 9 路读到 **0**（索引 3,4,5,6,7,26,27,28,30 —— 正好是 `NHBP*` 所在位置，该炮上没有 `HBP{n}T` 节点）；
- 索引 29 之后**整体错位一格**：`HBP30T` 读到 −1.31 T（实际是另一路信号，EFIT 期望 −0.156）；
- `HBP34T` 与 EFIT 的对应值**符号相反**。

**证据：与 EFIT 自己的输入卡逐点对照**

`/data/share/liuxj/workspace_physics/data/94048/5760/m094048.05760`（EFIT namelist）：

| idx | EFIT `EXPMP2` | fylite 取数 | 说明 |
|---|---|---|---|
| 0–2 | 0.19410 / 0.19199 / 0.17538 | 0.19626 / 0.19289 / 0.17488 | 吻合 |
| 3–7 | 0.13219 / 0.11460 / −0.15468 / −0.05969 / 0.14390 | **0 / 0 / 0 / 0 / 0** | 名字不存在 |
| 8–23 | … | … | 吻合（≤0.002） |
| 26–28 | 0.11576 / 0.08132 / 0.11189 | **0 / 0 / 0** | 名字不存在 |
| 29 | −0.15616 | **−1.30565** | 差 8 倍 |
| 31 | −0.12876 | 0.00064 | 错位 |
| 33 | +0.13747 | −0.12562 | 符号相反 |
| 36 | −0.00656 | 0.11036 | 错位 |

同一份 m 文件里其他量都对得上：`BTOR = -1.608`、`RCENTR = 1.8`、`PLASMA = 488492.09`、
`BRSP`（PF 电流 12 路）与 fylite 取数**逐位相同**；磁通环 35 路与数据集冻结值中位差 0.1%。

**影响范围**

`_valid_shots` 起点为 0 的所有炮号（≤97030）。实测 94048、95045、96000 三炮都是同样的 9 路读 0。

**后果**

- 94048 / 5.76 s：χ² 1.9e5–2.8e5，`没有一个竖直设定点收敛`；
- 94048 / 3.0 s、5.76 s 之外的时刻：部分能收敛，但用的是 29 路（其中若干错位）而非 38 路。

**已有的临时规避（在 fylite 侧，非最终方案）**

`apps/workflow/magnetic_live.py` 增加 `remap_early_probes()`：当设备卡 `_valid_shots[0] == 0` 且探针数为 38 时，
把取数用的节点名替换为遗留映射的 38 个名字，**位置仍用设备卡里的**。

效果（94048 / 4.21 s）：

| | 修复前 | 修复后 | EFIT g 文件 |
|---|---|---|---|
| 状态 | 未收敛 | **收敛** | — |
| q₀ | — | 1.933 | — |
| q₉₅ | — | 3.749 | — |
| χ²·mag | 6.6e4（4.0 s） | **81.6** | — |
| 磁轴 R | — | 1.870 | 1.881 |
| 门禁 | 未过 | 仅 `source_oscillation` | — |

**建议的修法（dev 侧）**

1. 按年代把真实的磁探针通道表（名字 + 位置 + 朝向）收进设备事实，早期版本不要用顺序命名；
2. 若定位数据确实缺失，至少在设备事实里标 `fylite:absent`，不要让消费方读到 0 还以为有值；
3. 建议同时核对磁通环（35 路）与 PF（12 路）在早期版本的命名——本次实测这两项是对的，但**探针一带出问题，另两类未必没隐患**。

**复现**

```
设备卡：artifacts/standalone-rc3-20261028/facts/device/east.jsonld（38 路 HBP1..38）
EFIT 输入：/data/share/liuxj/workspace_physics/data/94048/{4200,4500,5760,5900,7.2s}/m094048.*
遗留映射：data/eq/east94048/v1/mapping.json → B_PROBE_NODES_LEGACY（79 个名字）
```

## 问题 2：扫描失败时的错误信息不可诊断

**现象**

内核返回的 `tiers.M` 里已经有完整的逐候选扫描记录：

```json
"rounds": [{"round": 0, "scan": [
   {"zc": -0.03, "chi2": 335390.0, "q0": 0.107, "converged": false},
   {"zc": -0.026, "chi2": 167690.0, "q0": 0.118, "converged": false},
   …
]}]
```

但 `tiers.M.error` 只有一句：

```
"没有一个竖直设定点收敛"
```

**问题**

- 只看 `error` 无法判断是"位置没扫到"、"某通道坏了"还是"选项配置错了"——本次定位花了三轮才排除到选项/通道；
- 同一句错误对应了两种完全不同的成因：早期通道错配（问题 1）和 `options.loops = 'all'` 的配置问题。

**建议**

- `error` 里带上候选数量与首个失败原因（例如 `16 个候选全部未收敛，首个 zc=-0.03 chi2=3.4e5`）；
- 或在 `tiers.M` 增加 `error_class`，区分 `scan_no_convergence` / `channel_inconsistent` / `solver_refused`。

## 问题 3：`--run` 路径下输入卡的 `btor`、`target_ip` 不生效

**现象**

`demo.py --run <native.json>` 的内核请求只传 `{'settings', 'inputs'}`，从不读 `config['btor']`；
`target_ip` 会在 `demo.py` 内部被 `inputs.measurements.ip_observed` 覆盖。

**实测**

同一炮（164437 / 6.301 s），两套差异极大的输入卡：

| 输入卡 | btor | target_ip | q₀ | q₉₅ | χ² |
|---|---|---|---|---|---|
| 模板 | −1.608 | 488492 | 2.69601 | 2.18070 | 364.468 |
| 改写 | +2.476 | 699188 | 2.69601 | 2.18070 | 364.468 |

结果逐位相同。

真正的纵场入口是 `inputs.measurements.tf.f_vac_Tm`——把它乘以 1.5，q₀ 从 1.60188 变 2.40784、q₉₅ 从 6.42696 变 9.64049，严格按比例变化。

**问题**

`native.json` 里保留 `btor` / `initial.target_ip` 容易让集成方以为改了有效（本次就曾据此误判"纵场写错导致不收敛"）。

**建议**

- 在 `native.json` 结构说明里标注这两个字段在 `--run` 路径为**遗留/无效**；
- 或者让 `demo.py` 在检测到它们与 `measurements` 不一致时打印一条警告。

## 问题 4：发布包里没有纯磁适配器，导致双内核并存

**现象**

`v0.0.1-alpha-rc3/eq` 里有 `lib/libfylite_kernel.so`，但**没有** `demo.py`、`facts/`、`input/`；
纯磁工作流需要这些，原本指向 `artifacts/standalone-v3-20261027`，用的是另一份内核
（`libfylite.so` sha256 `84d31c8d…`），而不是 rc3 的 `f2632102…`。

**已做的处理（fylite 侧）**

用 rc3 的内核重新构建了适配器包：

```
artifacts/standalone-rc3-20261028/
    libfylite.so = rc3/lib/libfylite_kernel.so   f2632102…
    libsp.so     = rc3/lib/libsp.so              0170a30c…
    demo.py / facts/ / input/  ← 来自 standalone-v3
```

三处哈希已对齐：包内 `MANIFEST.sha256.json`、`archive_v3.py:EXPECTED_LIBRARY`、`demo.py:LIB_SHA`。

**验证**

rc3 内核与旧 standalone 内核在本路线上**数值完全一致**（七个算例逐项相同，含 164437/6.301 = 262 次 / q₀ 2.69601 / χ² 364.468）。

**建议（dev 侧）**

- 把纯磁适配器（`demo.py` + `facts/` + `input/`）纳入 rc3 发布，或由发布流程产出一份与 rc3 内核绑定的适配器包；
- 否则每次内核升级，应用侧都要手工重建一次适配器包，容易退回旧内核（本次就是这样）。
